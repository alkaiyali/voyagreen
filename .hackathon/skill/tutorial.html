Tutorial

Four hours, three people,
one harness that won't let you fake it.

This is a hands-on walkthrough of the hackathon harness: a tiny Node program that owns the phase state and refuses to advance until the work is real. By the end you'll know every command you need and why the gates exist.

The tool

harness.mjs — a state machine with gates. It drives idea → app → deck → script and blocks progress on missing, empty, or placeholder artifacts.

What you produce

A working demo, a demo-ready UI, a 4–5 slide deck, a memorizable script, and a backup recording — all generated from your own recorded answers.

The one idea: you shouldn't have to trust your own memory or optimism about what's done. The harness checks the disk, and only it decides when a phase is finished.

The mental model

Everything runs through eight phases. Each phase has a gate — a real check against real files. Run done and the gate runs: pass it and the harness advances, commits, and prints your next action; fail it and you get ✗ lines telling you exactly what's missing, and you stay put.

0ask→ 1idea→ 2spec→ 3build→ 4ui→ 5deck→ 6script→ 7rehearse

Three commands are your whole loop: status to resume, done to advance, and check when one gate behaves oddly. Everything else exists to feed those gates real material.

Never hand-edit .hackathon/state.json. The harness owns that file. To skip a gate on purpose, use done --force — it records the skip in .hackathon/log.jsonl so it's visible later instead of silently lost.

Quick start

The harness lives in this skill repo, but you never work inside it. Bootstrap a fresh project directory first — that copies harness.mjs into your idea's repo and git inits it, so the whole thing is self-contained.

1 · Bootstrap once

# from the skill repo
cd ~/repos/hackathon
node harness.mjs bootstrap ../my-idea

# then work inside your project from here on
cd ../my-idea

2 · Ask before you build — the agent runs the interview

The idea phase cannot pass without recorded answers. The harness owns the questions and the bar; the agent conducts the interview, rendering the questions with its own question tool. Only three are required: the idea, who it's for, and the one core feature. Capture the answers verbatim — the deck and script are built from the user's own words, never from the agent's guesses.

node harness.mjs ask --json     # schema: id/header/options/required/why
node harness.mjs ask --pending  # only what is still missing or thin

3 · Record the answers — then close the gaps

intake writes HACKATHON.md, SPEC.md, and .hackathon/answers.json straight from the user's words. --report returns a machine-readable gap list so the agent can re-ask only what is weak — and intake merges, so a second pass never wipes the first.

node harness.mjs intake --answers answers.json --report  # { ok, gaps:[…] }
node harness.mjs ask --pending                            # re-ask only those, then intake again

Quality in, quality out. The gap report has three tiers: missing (blocks the gate), thin (present but too vague to pitch), and recommended (absent — and it will cost you a slide or a beat later). The optional fields are what make the pitch: --pain, --painPoints, --hook, --how, --hardPart, --pitch30, --qa "question|answer", --demo, --domainObject, --event, --team. Skip one and the generator drops what it can't source.

Stack defaults to a single-file static HTML. Zero install, fastest to a demo, and every gate (serve, screenshot) works with no tooling. Only reach for Vite + React if the idea genuinely needs routing or shared state — an npm install costs 15–30 minutes of a 240-minute budget.

Working the loop

From inside your project directory, the loop is two commands. Keep status open in a second terminal if you can.

node harness.mjs status   # phase, clock, gate results, the single next action
node harness.mjs done     # run the gates; advance ONLY if they pass

The plan stays visible, and it can't drift from reality because the harness maintains it from the same definitions the gates use:

node harness.mjs goals      # current goal + owners + success criteria (GOALS.md)
node harness.mjs timeline   # phase windows against your deadline (TIMELINE.md)
node harness.mjs note "..." # decisions and learnings (NOTES.md)

Resuming in a new session? Run status. It prints the phase and the next action — and never re-ask a question already recorded in SPEC.md or answers.json.

Phases & gates

This table is the contract. The right column is what the gate actually verifies before it will let you move on.

2specSPEC.mdpitch, core feature, demo path, stack, cut list; ≥ 3 concrete demo steps
3buildthe appstarts and serves real content (> 300 bytes), no template tokens
4uidemo-ready UIno lorem ipsum, screenshot captured, seed data referenced

Start each phase with status, work until the artifact exists, then run done. Run node harness.mjs smoke any time you just want a quick "does my app actually serve?" check.

Generate the deck & script

The deck and the script are generated from the same recorded answers, so they can't drift apart. Regenerate both after any change — never hand-edit one and leave the other stale.

Two deck lanes

Lane M (default) writes deck/slides.md and renders it through Marp. Lane H writes a bespoke, self-contained deck/slides.html — no render step, no Marp — and it ships an animation engine: data-anim entrances, per-slide data-transition, a live atmosphere canvas, data-morph objects that travel between slides, and data-build for press-to-advance reveals. Add --html to choose it. If both files exist, Lane M wins — delete slides.md to present the HTML one. The gate and the script parse both lanes the same way.

# once the app runs, record real demo numbers for the impact slide
node harness.mjs impact "Hours saved per week=5" "Blockers surfaced=3"

# deck ← answers.json; pick a lane, then render + review
node harness.mjs deck --init --force          # Lane M → slides.md (Marp)
node harness.mjs deck --init --force --html   # Lane H → slides.html (bespoke)
node harness.mjs deck --images               # review PNGs, either lane

# script ← deck; the two stay in sync
node harness.mjs script --init --force

The split that matters: facts vs. voice

The generator supplies structure and facts — slide order, titles, demo steps, stack, numbers, names. It never invents your voice. Any line it had to author is stamped so you can't mistake it for the real thing:

**Say:** "Here are the three things you're about to see."  **[DRAFT — rewrite in your own voice]**

The script gate will not pass while a [DRAFT] remains. That's deliberate: generic filler must not reach the stage wearing your voice. Replace each flagged line — or supply --hook, --how, and --qa at intake and regenerate, and the drafts disappear.

A deck you have not seen is not a deck. Open deck/slides.html or the slides.*.png review images and look at them. The script gate enforces the sync too: every beat names a real slide, slide numbers only move forward and cover the whole deck, and titles must match the deck source (deck/slides.md or deck/slides.html) exactly.

Command reference

CommandWhat it does
bootstrap <dir>Install the skill into a new project and git init it.
init <name>Start the clock (--hours 4 --deadline 18:00).
ask [--json]The intake question schema — --json for an agent's question tool; --pending for only what's missing or thin.
intake …Record the answers (merges over what's on disk); --report returns the machine-readable gap list.
impact "m=v" …Record real demo numbers for the deck's impact slide.
deck --initGenerate the deck from answers — deck/slides.md (Marp) or --html for a bespoke deck/slides.html; --images renders PNGs.
script --initGenerate script.md, synced to the deck.
status [--json]Run first every session. Phase, clock, gates, next action.
check [phase]Run the gates for one phase in isolation.
done [--force]Run the gates; advance only if they pass.
verifyRun every gate up to the current phase.
smokeQuick "does the app actually serve?" check.
goals / timelineRegenerate GOALS.md / TIMELINE.md from the gates.
note "…" / log "…"Append to NOTES.md / the audit log.

When it breaks

SituationDo
"You cannot advance"The ✗ lines name exactly what's missing — fix those.
Skipping a phase on purposedone --force; records the skip in .hackathon/log.jsonl, and status keeps showing it.
Lost your place / new sessionnode harness.mjs status — it prints the phase and the next action.
One gate failing oddlynode harness.mjs check <phase> runs just that gate.
Everything, all at oncenode harness.mjs verify runs every gate up to the current phase.
App won't start for the gatesAdd .hackathon/config.json: {"START_CMD":"npm run dev","PORT":5173}.
Deck render fails offlineLane M only. Run once with wifi: npx @marp-team/marp-cli --version, then it's cached — or switch to the HTML lane: deck --init --html.
Screenshots failInstall Chrome or Edge; the UI gate degrades to a warning without one.

Requirements: Node 18+. The build, ui, and rehearse gates start your app, so they need Python 3 (static apps) or your package manager; the ui gate needs Chrome or Edge for screenshots.

On stage

script.md

The operator keeps the cue sheet at the top open — every beat says ▶ ADVANCE to Slide N after "…", HOLD, or END.

deck/slides.html

Open full screen. In the HTML lane this file is the deck — arrow keys / space advance, f is fullscreen; in the Marp lane it's the render. Review the PNGs before you present.

demo-backup.mp4

If the live demo dies, play this and keep talking. Live demos fail; video doesn't.

If asked how you built it

Say plainly: "we used AI coding tools." Transparency is the strategy.

Rules to keep

Deck and script are generated from the same answers — regenerate both after any change. Never ship a [DRAFT] line. Never hand-edit .hackathon/state.json. If you must skip a gate, record it with --force. On ambiguity, take the fastest reasonable call, log it, move on. And deck + script always outrank UI polish — cut UI first, never the deck.

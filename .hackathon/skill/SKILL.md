# Hackathon Loop

You are running a time-boxed hackathon. This skill is **harness-driven**: a small
Node program owns the phase state and refuses to advance until real artifacts
exist on disk. Do not track phases in your head and do not hand-edit the state
file — ask the harness.

Think in goals, not commands. `.hackathon/GOALS.md` (regenerated by the harness on every
transition, from the same definitions as the gates) is the objective list with
owners and success criteria — read it at the start of every session instead of
reconstructing the plan. `.hackathon/TIMELINE.md` is the phase windows against your
deadline. `.hackathon/NOTES.md` is your scratchpad: write every decision and learning there
with `node harness.mjs note "..."` — future-you resumes from notes, not memory.
The commands are the engine underneath: they check the work and refuse to advance
until it is real.

## Where things go — keep the root clean

```
<project>/
├── HANDOFF.md      ← the team starts here: what's ready, what's left for them
├── harness.mjs     ← the one command
├── present/        ← everything the team shows or ships
│   ├── app/        the product — build it HERE (index.html, package.json, src/…)
│   ├── deck/       slides.html, theme.css, palette.css, assets/
│   ├── script.md   the demo script with the operator cue sheet
│   └── demo-backup.mp4
└── .hackathon/     ← everything the agent uses
    ├── SPEC.md HACKATHON.md GOALS.md TIMELINE.md NOTES.md
    ├── answers.json (recorded) · intake.json (your draft) · state · log · evidence/
    ├── context/    the user's notes and briefs
    └── skill/      this project's own copy of the hackathon skill
```

(`.claude/` and `.opencode/` sit at the root too — hidden, and only because
those tools look there: a link to `.hackathon/skill` and the two subagents.)

**Never write a file to the project root** other than those two. Scaffold the
app inside `present/app/` (e.g. `npm create vite@latest present/app`), keep
scratch files in `.hackathon/`, and put nothing else at the top level. Older
projects: `node harness.mjs tidy --apply` moves everything into place.

## Autopilot — one prompt in, pitch-ready out

**Use this whenever you are given an idea, context files, or the word
"autopilot"** and no one asked to be interviewed step by step. One loop, no
check-ins. Stop only for the human-only items listed at the end.

**0 · Set up (skip if `.hackathon/state.json` already exists here).** With this
skill's own directory as `<skill>`:

```bash
node <skill>/harness.mjs start <dir> --name <slug> [--hours 4] [--deadline HH:MM] --context <files or dirs…>
```

Then run every harness command from inside `<dir>` (`cd <dir> && node harness.mjs …`).
Pick `<dir>` as a sibling of the current directory, named after the idea, unless
told otherwise.

**1 · Intake: infer, don't interrogate.** Read the prompt and every file in
`<dir>/context/`. Every question in `ask --json` has a `by` field:

- **`by: "agent"`** — who it's for, the core feature, the demo path, domain
  object, stack, pain, the person, hook, closer, Q&A, next… **Derive these
  yourself** from the idea, the context and common sense. A student-alert app is
  for students; its core feature is the alert; its demo is pick → trigger →
  receive. Do not ask the user what an idea obviously implies. List every field
  you wrote in `"decided": [...]` so the handoff asks the team to make it theirs.
- **`by: "user"`** — the idea itself, event, team, time budget, real proof. Only
  a person knows these.

Then ask **only** `node harness.mjs ask --pending --user --json`, in **one**
round, right after intake: **the teammates' names and the hackathon's name are
always asked** (the cover and closing slides show them — never fill in a generic
"Hackathon", never invent names), plus the idea if it is missing. Do not block on
the answer — keep building and record it when it comes
(`intake --team "…" --event "…"`, then regenerate deck + script). Proof is not
asked up front; it becomes a handoff item. See *Asking well* below.

- **`appName`**: the product's name exactly as it should read on the slides
  ("VoyaGreen", not the slug's "Voyagreen"). Take it from the brief; add it to
  `decided` if you chose it.
- **`stack`**: a brief that says mobile / mobile-first / app gets **React
  Native (Expo)** — see Phase notes → spec.

- *`character`*: from the context if it describes a real person; otherwise a
  composite built from the context — and add `character` to `decided`.
- **Never invent facts**: no `proof` numbers, no traction, no users, no quotes.
- Record the context files in `"sources": [...]`, then
  `node harness.mjs intake --answers .hackathon/intake.json --report` and fix any `thin`.

Say in one short message what you inferred (who, core, demo path) and carry on —
the user can interrupt; do not wait for a confirmation.

**2 · The loop.** Repeat until `stop` is true:

```bash
node harness.mjs next --json    # { phase, gatesPass, fail[], action, stop, human[] }
# … do the phase's work (below), fixing every line in fail[] …
node harness.mjs done           # advances only when the gates pass
```

| Phase | Your work in autopilot |
|---|---|
| idea | intake (step 1) |
| spec | refine .hackathon/SPEC.md: demo path you will actually build, **a cut list that is honest**, the domain object, accent and type lane; run `palette "<accent>"` so the app and the deck share it. When `done` passes, **launch `@deck-designer` in the background** (below) |
| build | build the demo path in `present/app/`, in order; `smoke` until it serves (Expo: `npx expo export -p web` first) |
| ui | link `present/app/palette.css` (Expo: import `palette.js`) and use its tokens (statuses on `--success`/`--warning`/`--danger`); seed real-looking data from the context; Design rules; **open `.hackathon/evidence/ui.png` and look at it** |
| deck | wait for `@deck-designer`; `deck --init --force` (places the app screenshot, keeps theme.css); `deck --images`, look; `done` |
| script | the designer already wrote it — `check script`, fix what is left, `done` |
| rehearse | **stop** — `node harness.mjs handoff` |

**The deck is built in parallel.** As soon as `spec` passes, start the
**`@deck-designer`** subagent in the background and go straight on to `build`.
It is the team's pitcher: it writes the prose, generates `present/deck/slides.html`,
designs it in `present/deck/theme.css`, looks at every slide, and generates the synced
`present/script.md` — while you build the app. The lanes never cross:

| | owns (writes) | never touches |
|---|---|---|
| **you** (driver) | app source, .hackathon/SPEC.md, phase state (`done`), commits | `present/deck/`, `present/script.md` while the designer runs |
| **@deck-designer** (pitcher) | `present/deck/`, `present/script.md`, prose intake fields | app files, .hackathon/SPEC.md, `done`, git |

Do not write `.hackathon/answers.json` while it runs (`impact` waits until it
reports back). The agent file pins its model — **Opus 5.5** in Claude Code,
**muse-spark-1.3-contributor** in OpenCode — so the design pass gets the chosen
design model while you keep building.

**The design pass is the designer's, never yours.** If `@deck-designer` is not
in your subagent list, do **not** design the deck with your own model and do
not write `present/deck/theme.css`. Do the non-design steps yourself (prose,
`deck --init --force`, `script --init --force`), advance, and let the handoff
flag the missing design pass — then tell the user: run
`node <skill>/harness.mjs install` and restart the session. If your tool can run
the subagent but only in the foreground, run it in the foreground.

On `REFUSED`, fix the ✗ lines and run `done` again. **Never `done --force` in
autopilot** — after 3 failed attempts on the same phase, stop and report the
failing lines instead. A skipped gate is a decision for the team, not for you.

**3 · Hand off.** `node harness.mjs handoff` writes `HANDOFF.md`: what is ready
(app, deck, script) and what only a human can do — record `present/demo-backup.mp4`,
run the poll for real proof, rewrite agent-written lines in their own voice,
rehearse out loud. End your turn with that list. Do not fake any of it.

## Ask first — never invent the idea

(Interactive mode. In autopilot, the prompt and context files *are* the answers —
step 1 above.)

**If the user has not given you an idea, ask for one. If the idea is partial, ask
only for the gaps.** Do not research, scaffold, or write a single file before
there are answers on disk.

The harness owns the **questions and the bar**; you conduct the **interview**.

```bash
node harness.mjs ask --json     # the schema: id/header/type/options/required/why
node harness.mjs ask --pending  # only what is still missing or thin, against .hackathon/answers.json
```

**You are the interviewer, not a relay.** Ask the idea first; then, for every
`by: "agent"` question, **propose** instead of asking open-ended — "It's for
Metro Manila students who guess every rainy morning — right?" — and let them
correct you.

**Asking well** (both modes):
- A `select` question has `options` — pass them through.
- A free-text question has **no** options. Either ask it as a plain message, or
  offer **2–3 concrete candidates you inferred** as the options. **Never add an
  "I'll type it" / "Other" / "Let me write it" option** — every question tool
  already has its own free-text choice, and a fake one just sends the user to a
  dead end.
- Batch related questions in one round; never ask what the prompt or context
  already says. Then capture their words
**verbatim** — the whole point of the phase is that the deck and script are built
from *their* answers, never from your plausible-sounding guesses.

```
Required, first:  idea · then PROPOSE who & the win · the ONE core feature
Then, batched:    demo path (3 steps) · domain object · stack · time budget
Pitch-fillers:    the person · pain · pain bullets · opening line · local proof · closing line ·
                  hard Q&A (incl. what doesn't work yet) · 30s pitch · event · next · team
```

Record, then let the harness tell you what is still weak — don't decide that
yourself:

```bash
node harness.mjs intake --answers .hackathon/intake.json --report   # -> { ok, gaps:[...] }
```

`--report` returns the machine-readable view: `missing` (blocking), `thin`
(present but too vague to pitch), and `recommended` (absent, and it will cost you
a slide or a beat later). On gaps, re-ask **only those** — `ask --pending` lists
them, with the reason — and record again. `intake` **merges** over what is already
on disk, so a second pass never wipes the first; `--fresh` resets. Loop until the
blocking and thin gaps are gone, or the clock says ship what you have.

`intake` writes `.hackathon/answers.json`, `.hackathon/HACKATHON.md`, and `.hackathon/SPEC.md` from the
user's own words, so the idea gate passes on real input instead of your
assumptions. If they gave no demo path, the harness proposes one and **flags it
as a proposal** in both the output and the gate — confirm it with them.

Rules for asking:
- Never invent a **fact** — the `by: "user"` answers and any number, user or
  quote. Derive the `by: "agent"` ones and mark them `decided`. "You decide" is an
  answer — decide, then `harness.mjs log "decided X because Y"`.
- Follow up on **thin**, not just missing: a one-word pain point is worse than a
  blank one, because it will reach the stage looking answered.
- Never ask for something `.hackathon/SPEC.md` already answers, and never re-ask what
  `--pending` did not list.
- If they gave you an idea up front, skip straight to `intake` — but still record it.

## Start here

```bash
node harness.mjs init <project-name> --hours 4 --deadline 18:00
node harness.mjs status
```

`status` prints the current phase, the clock, the gate results, and the single
next action. **Run it at the start of every session** — it is the resume point.

Keep it open in a second terminal: `while true; do clear; node harness.mjs status; sleep 30; done`

## Working the loop

| # | Phase | You produce | Gate checks |
|---|-------|-------------|-------------|
| 0 | **ask** | `.hackathon/answers.json` | — (intake refuses without idea / who / core) |
| 1 | **idea** | `.hackathon/HACKATHON.md` | **intake recorded**, idea ≥ 40 chars, one core feature, no placeholders |
| 2 | **spec** | `.hackathon/SPEC.md` | pitch, core feature, demo path, stack, cut list; ≥ 3 concrete demo steps |
| 3 | **build** | the app | app **starts and serves real content** (>300 bytes), no template tokens |
| 4 | **ui** | demo-ready UI | no lorem ipsum, screenshot captured, seed data referenced |
| 5 | **deck** | `present/deck/slides.html` | builds with **zero** placeholders, 4–5 slides, numbers measured-with-source or labelled projection, nothing cut claimed as built |
| 6 | **script** | `present/script.md` | 100–340 spoken words, ≥ 4 beats, 30-second version, Q&A, opens on the story and ends on the closer, and **synced to the deck**: every beat names a real slide, titles match, no slide uncued |
| 7 | **rehearse** | `present/demo-backup.mp4` | recording ≥ 15s, **cold restart** passes, deck + script gates still green |

Each phase is "done" when its command says so, not when it feels done.

## Phase notes

**1 — idea.** Already handled by `intake`: it writes `.hackathon/HACKATHON.md` with the idea,
who it is for, the core feature, the demo path, and the team. Only edit it to add
detail, never to replace the user's answer with your own.

**2 — spec.** `intake` scaffolds `.hackathon/SPEC.md`; refine it. Elevator pitch · Core feature
· Demo path (3 steps, numbered) · Stack · Cut list. The demo path must be steps you
will actually click in order — slides and script both follow it.

**If the brief says mobile, mobile-first, or "app", build React Native with Expo.**
A web page in a phone frame does not meet a mobile brief — judges and mentors
call that non-compliant. The Expo lane:

```bash
npx create-expo-app@latest present/app --template default   # Expo Router, static web output
# delete the template's example screens/components; then
cd present/app && npx expo install react-native-svg expo-linear-gradient
```

- **Make it feel like a real app**: a pseudo onboarding (2–3 pages with the
  domain object as art, then a one-screen setup: name, interests, preferences —
  no account), a tab bar (home / saved / profile), detail screens, empty states.
  Pre-fill setup with the demo persona so the live path is one tap per step.
- **Colours from `present/app/palette.js`** — `palette` writes it next to
  palette.css, same tokens as the deck: `import { palette } from '../palette'`.
  Status stays on `success` / `warning` / `danger`, never the accent.
- **Type**: bundle the lane's fonts as assets (`useFonts`) and **render
  without waiting for them** — a screen that returns `null` until fonts load
  exports as an empty shell and fails the build gate.
- **Dynamic routes need `generateStaticParams`** so every demo screen is
  pre-rendered.
- **The gates judge the web export**: run `npx expo export -p web` in
  `present/app` before `smoke`, `check build`, `check ui` and `done`. The harness
  serves `dist/` with clean URLs (`/trip/abc` → `trip/abc.html`). On the
  projector, show that same build — it renders inside a phone frame on a wide
  screen; on a phone, run it in Expo Go (`npx expo start`).

**Otherwise, single-file static HTML is the default** (`index.html` + one JS file, no
build step, no `npm install`). The gate serves and screenshots it with zero
tooling, on any OS. Escalate to Vite + React only if the idea genuinely needs
it: multiple screens with shared state, client-side routing, or an npm-only
library the wow moment depends on. An npm install plus dev-server wrangling
costs 15–30 minutes of a 240-minute budget — spend it only for a reason. Add a
backend only if the wow moment needs one.

**3 — build.** Build the demo path first, in order. No refactors, no abstractions
"for later". Run `node harness.mjs smoke` whenever you want a
quick "does it actually serve" check. The gate starts your app, fetches it, and
requires real content — a shell with an empty `#root` fails.

**4 — ui.** Seed data with real-looking names and numbers. Make the wow moment
loud: one big number, one chart, one animation. Hardcode anything fragile; the
demo path must never error. The gate screenshots the running app to
`.hackathon/evidence/ui.png` — **open that file and look at it.**

**5 — deck.** The deck is **generated from the recorded answers**, not written from
scratch, as one self-contained HTML file:

```bash
node harness.mjs deck --init --force   # present/deck/slides.html from .hackathon/answers.json
node harness.mjs deck --images         # check it + one review PNG per slide
```

`present/deck/slides.html` **is the presentation** — no render step, no install, no
network. It ships a fixed 1280×720 stage that scales to any screen, keyboard /
click / fullscreen navigation (`←` `→`, `space`, `f`), deep-links (`#4`), a
progress bar, print-to-PDF, and the object morph below. Each slide is a
`<section class="slide" data-title="…">`. **Put the design in `present/deck/theme.css`**
— it loads after the template's styles, and `deck --init --force` never
overwrites it, so regenerating after new answers keeps the look. Content edits
made directly in `slides.html` are lost on regeneration; route content through
the answers instead.

The theme uses the **Lane A type pairing** (Satoshi for the whole deck, Azeret
Mono for code) exposed as `--font-display`, `--font-body` and `--font-mono`,
bundled with the skill and copied to `present/deck/assets/fonts/` by `deck --init`
— the deck loads **nothing** from the network, so the first paint is the cover,
never a blank (or, in a dark-mode browser, black) page while a font CDN crawls
on venue wifi.
Swap those tokens only within a vetted lane — see the Design rules.
**Light first, like product motion design.** The deck is light by default — a
projector in a lit room washes dark slides to grey, dark type on white
survives. The look follows product-launch motion: soft blooms of the brand
colour drifting in from the edges, faint grid squares floating up, dark
headline type, white cards with soft shadows, and the product's own UI as the
hero. (`palette --dark` flips the whole deck to the cinematic dark engine for a
dark room.)

**Motion is choreographed, not decorated.** Every slide change is a view
transition in which both slides move — the old one exits fast, the new one
arrives — while the atmosphere surges underneath. The house transition is
`focus`, a camera focus-pull (the old shot racks out of focus as it drifts, the
new one pulls in); `zoom` pushes the camera into the problem; **one** `sweep`
(bars of the brand colour) is the showpiece, landing on the **flood** slide —
Impact, full-bleed brand colour, the big number as huge type. On the slides:
the title **reveals** (wipes on, sharpens, settles), the one-liner **rises**
in, and the demo steps sit in a card whose spinners **tick to
checks** one by one (`data-anim="reveal|rise|checklist"`). No typewriter
effect — a line the room has to wait for is a line they stop reading. Slide titles roll
like an odometer and headings rise in word by word (`data-anim="split"`). The
**hero object** — the domain object, set once in `theme.css` as `--object` —
sits on every slide at a different crop and scale and glides between them. One
transition language plus one showpiece reads as a film; six different
transitions read as a template. Screenshots (`?still=1`) and reduced-motion
viewers get static slides.

Tag any other object to make it travel (**object morph**): give the same object
`data-morph="key"` (or `class="morph"`) on two consecutive slides and it glides
between them on the same spring — PowerPoint Morph / Keynote Magic Move:

```html
<img data-morph="hero" src="assets/hero.jpg"
     style="position:absolute; right:72px; bottom:80px; width:300px">
```

Put the same tag on a later slide at a different size/position and it travels
(a screenshot growing into the page, a product shot gliding across). `build-deck`
injects the naming script; only tagged foreground objects morph (CSS
backgrounds cannot). The template also ships a **CSS MacBook running
a fake TUI** (`.mac`, `.mac-screen`, `.mac-base`, `.tui`) you can use as the morph
object with no image at all — size it with an inline `width` and everything
inside scales via container units.

**The real app is placed automatically.** Once the ui gate has captured
`.hackathon/evidence/ui.png`, `deck --init --force` copies it to
`present/deck/assets/app.png` and puts it on "What we built" (the ASCII flow steps aside
for it). Before that, the slide simply has no screenshot — never an empty frame.
`@image-scout` is **optional** and bounded (one inline SVG on one named slide,
8 tool calls); do not run it in autopilot.

`--init` fills the template from `.hackathon/answers.json`: title (`appName`,
exact casing — else the slug), one-liner (`oneLiner`, else the idea's first
sentence), the problem headline and bullets, the 3-step demo TOC, the
how-it-works diagram from your core feature, the stack, the impact table, and
the **closing slide** — the closer as big type, titled with its tagline, over the
team's names. There is no "What's next" slide: `next` feeds the Q&A, not the
deck. **The cover shows the event name above the title and the teammates'
names below it — only as the team gave them.** No event recorded → no kicker;
never a generic "Hackathon · <month>". **It never invents content** — elements
with no recorded data are dropped and the slides that would be hollow (impact)
are removed entirely. It prints what you skipped, so you can go sharpen it.

The **Impact** slide holds two kinds of number, kept visibly apart: **measured
proof** the team gathered (`--proof "23 of 30 students we asked … | hallway poll,
Grade 11, Sep 30"` — a claim without a source is rejected), and **projections**
from seeded demo data, labelled as such on the slide. Proof comes first. A 20-minute
poll of 20–30 real people beats any national statistic.

Record demo numbers once the app runs, then regenerate to add the impact slide:

```bash
node harness.mjs impact "Hours saved per week=5" "Blockers surfaced=3"
node harness.mjs deck --init --force
```

Then **look at the output** — open `present/deck/slides.html`, or the review images in
`.hackathon/evidence/deck/`. A deck you have not seen is not a deck. You may hand-edit it
afterwards; the gate reads slide titles from `data-title` on each
`<section class="slide">` (or the section's first `<h1>`/`<h2>`) and only cares
that it checks clean. Because the script is generated from the same parser, a
hand-renamed slide keeps the two in sync.

**6 — script.** Generated from the deck, so the two cannot drift:

```bash
node harness.mjs script --init --force
```

**The split that matters: facts vs. voice.**

The generator supplies *structure and facts* — slide order, titles, the demo steps,
stack, numbers, names. It **never invents your voice**. Any line it had to author
rather than take from the intake is stamped:

```
**Say:** "Here are the three things you're about to see." **[DRAFT — rewrite in your own voice]**
```

and the script gate **refuses to pass while a `[DRAFT]` remains**. Ask the intake
for the prose and the drafts disappear:

```bash
node harness.mjs intake --hook "<your opening line>" \
  --how "<how it actually works>" --hardPart "<what was genuinely hard>" \
  --pitch30 "<what you'd say with 30 seconds and no demo>" \
  --qa "<hardest question>|<one-line answer>" --qa "<next>|<answer>"
```

If the user did not supply prose, **you write it** — you have the answers and the
context, so rewrite each flagged line in their project's voice. Do not leave a
`[DRAFT]` in place; that is the one thing the gate will not let you skip.

**The live demo is cued as a round trip.** On "What we built" the presenter
says "Let me show you it working" and the operator gets `⇄ SWITCH to the app`;
the demo steps are marked **Screen: the app**; the last step carries
`⇄ SWITCH back to the deck, Slide N`; then the how-we-built-it line plays on the
same slide. The cue sheet has a Screen column, and the script gate fails if a
switch to the app has no switch back — the operator is never stranded on the app.

The deck is the source of truth for slide titles and order, and every beat carries
an explicit operator cue naming the slide to move to and the words that trigger it
(`▶ ADVANCE to Slide 4 after "...into a dated task"`), so the operator reacts to
the presenter's line instead of guessing. A cue sheet table at the top is their
standalone cheat sheet.

The gate also enforces the sync: every beat must reference a real slide, the slide
numbers must cover the whole deck and only move forward, and the titles must match
`present/deck/slides.html` exactly. Rename a slide
and the gate fails until you regenerate.

Then **look at it** and run it out loud. If it exceeds 2 minutes, cut the
how-it-works beat first — hand-written scripts can use
[templates/demo-script.md](templates/demo-script.md) as the shape reference.

**7 — rehearse.** Cold-restart the app, walk the demo path, and **record
`present/demo-backup.mp4`** — live demos fail and video does not. Time the run-through
out loud; if it exceeds 2 minutes, cut the how-it-works beat first.

## Team of 3, 4 hours

- **Driver** — runs this loop: spec → build → ui. Owns the app.
- **Pitcher** — in parallel from ~minute 30: deck + script from .hackathon/SPEC.md's real
  feature names. Never waits for the app to be finished.
- **Runner** — content and clock: seed content, stats, team names; records the
  backup demo; calls out the clock.

Budget: idea+spec 15m · build 120m · ui 30m · deck+script 45m · rehearse+buffer 30m.
Deck and script outrank UI polish — always. Cut UI first, never the deck.

## Design rules

These apply to the app UI **and** the deck. They are cheap, and they are the
difference between a demo that looks designed and one that looks generated.

1. **Pick ONE domain object and repeat it.** An image, an SVG or a 3D model — one
   object from the product's own world (a capsule, a blister pack, a pulse
   trace, a lens, a syringe). Put the *same* object in the deck's hero, the app
   icon, empty and loading states, section dividers, the favicon — at different
   crops, scales and angles. Repetition reads as identity; a family of six
   different icons reads as stock. Choose something the product physically
   touches — abstract blobs lose.
2. **Type and icons are chosen, never inherited.** Use one vetted lane for the
   whole project — app **and** deck:
   - **Lane A (default)** — **Satoshi** (display + body) · **Azeret Mono** ·
     **Mynaui** icons. Product / personality. The deck template ships this.
   - **Lane B (dense / technical)** — **IBM Plex Sans** · **IBM Plex Mono** ·
     **Fluent** icons (regular for default, filled for active). For data-heavy
     tools and dashboards.

   The defaults — Inter, Roboto, JetBrains Mono, Open Sans, Lato, Montserrat,
   Poppins, bare `system-ui` — are the single loudest "untouched template" tell
   there is; so is a generic icon pack. **No Lucide, Heroicons, Feather, Font
   Awesome, Material Symbols, Bootstrap Icons, Phosphor or Tabler.** Inline the
   icons as SVG at the chosen weight; never ship an icon font or the runtime. A
   hand-built (or well-chosen) icon reads as yours; a default set reads as
   everyone's. Drifting outside a lane? It must still be distinctive — not the
   stock six.
3. **A palette, not a colour — generated, never hand-picked.** Choose one
   accent, then `node harness.mjs palette "#E8A33D"` — **light by default**, for
   projectors (`--dark` only for a dark room). It writes `present/app/palette.css`
   (the app) and `present/deck/palette.css` (the deck) — the same tokens, so they read as
   one product — built in OKLCH: a neutral ramp (cool slate under a warm accent;
   warm on warm is mud), the accent lifted if needed to pass contrast, a
   50–900 accent ramp, and success / warning / danger / info that stay clear of
   the accent. Every text pairing clears WCAG AA, and the ui and deck gates fail
   anything that doesn't. Then:
   - **Accent is emphasis only**, ~10% of the screen: the key number, the primary
     button, the active state. Never a blue→purple gradient.
   - **Never fade the accent with opacity** — a translucent accent over a dark
     ground turns to mud. For a quieter accent use a ramp step (`--accent-700`).
   - **Status is never the accent.** Taken / done → `--success`, due soon →
     `--warning`, missed / error → `--danger`. An amber brand does not make
     "taken" amber — amber means caution. Pair status colour with a label or icon.
   - Glows and atmosphere use `--glow` (low-chroma), never the raw accent.
   - `--accent` is the exact brand colour, for fills; `--accent-text` is the same
     hue made readable as text on the background. Use each for its job.
   - SVGs cannot read CSS variables: use the hexes `palette` prints.
4. **The real product is the hero image.** No stock photography, ever. A
   screenshot of the working app beats any photo — `deck --init` places it.
5. **Atmosphere is procedural.** Light, vignette, grain, and one surface
   treatment (glass, flat, outlined — pick one) applied consistently. Depth comes
   from CSS, not from decorating every card.
6. **Empty space is allowed.** Filling space is how decks get soulless.

Record the object, the accent and the type pairing in `.hackathon/SPEC.md` so all three of
you use the same ones, then reference them from both the UI and the deck.

## Pitch rules

Judges decide fast from a story, then use the details to justify it. They are
not less sharp for it — everyone judges that way under time pressure, and a panel
watching pitch after pitch all day is under a lot of it. So lean in, **inside one
hard line: persuade as hard as you can, but every claim must be true and
demoable.** A great story about a real, working app is what should win; a great
story about features that do not exist is exposed by one question.

0. **The order: Problem → Reveal → Demo → Impact → Close.** The person and the
   problem first; then the reveal — an optional ~10 s motion piece at
   `present/deck/assets/reveal.mp4`, which `deck --init` turns into a full-bleed slide
   that plays muted and advances itself; then the live demo, while the room
   still cares; then the measured number on the flood slide; then the closer.
   Never open on the video (a solution before the problem, and your riskiest
   click first) and never end on it or on the live app (the last line is the
   spoken closer). Keep the video ≤ 15 s and make it work without sound.
1. **The first 30 seconds are the person and the problem.** Never the team name,
   a greeting or a feature list. *(script gate: the opener cannot start "Hi / We
   are / Our app / This is…")*
2. **One named person beats any statistic.** "Bea, Grade 11, refreshing five
   Facebook pages at 5 AM" — record it as `character`; it leads the problem
   slide and the opening beat.
3. **Real local proof is gold.** Poll 20–30 people who have the problem; "23 of
   30 students we asked…" with how you asked. Measured and projected numbers are
   never mixed. *(deck gate)*
4. **Polish reads as competence** (the halo effect): a clean demo path makes judges
   assume clean code. It is why the UI phase exists — but it still ranks below the
   deck and script.
5. **End strong.** Judges remember the last line: the impact plus a tagline
   (`closer`). Never "thank you, any questions?" *(script gate)*
6. **Prepare for the judge who probes.** At least 3 hard questions, including
   what does not work yet or what is faked — answered calmly and truthfully. If
   the team has not prepared it, the script adds it as a draft the gate blocks on.
7. **Nothing cut is claimed.** A feature on the SPEC cut list may appear only as
   future ("next", "not yet") — never as built. *(deck + script gates)*
8. **Confidence and energy carry a tired panel.** Not checkable — rehearse the
   full run once in front of a teammate playing the probing judge.

Never let "the judges won't notice" become the mindset. It leaks into delivery
and makes you careless in exactly the Q&A where one judge will probe.

## Rules

- **Deck and script are generated from the same answers.** Regenerate both after
  any change — do not hand-edit one and leave the other stale (`deck --init --force`,
  then `script --init --force`).
- **Never ship a `[DRAFT]` line.** The generator supplies structure and facts;
  the voice is the user's or yours. The script gate blocks until every draft is
  replaced.
- **Never hand-edit `.hackathon/state.json`.** Use the harness.
- If you must skip a gate, use `done --force`; it records the skip in
  `.hackathon/log.jsonl` so it is visible later.
- Ambiguity: take the fastest reasonable call, `harness.mjs log "..."` it, move on.
- **Every claim must be true and demoable** — see Pitch rules. Seeded numbers
  are called projections; cut features are called next.
- If asked how it was built, say plainly: "we used AI coding tools." Transparency
  is the whole strategy.
- Resuming? `harness.mjs status`, then continue from `next`. Never re-ask a
  question already answered in `.hackathon/SPEC.md` or `.hackathon/answers.json`.

## If the harness misbehaves

- `harness.mjs check <phase>` runs one gate in isolation.
- `harness.mjs verify` runs everything up to the current phase.
- Gates need Node 18+. The `build`/`ui`/`rehearse` gates start your app and need
  Python 3 (static apps) or your package manager. The `ui` gate needs Chrome or
  Edge for screenshots; without a browser it degrades to a warning.

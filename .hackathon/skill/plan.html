The rule that saves hackathons: deck and script outrank UI polish — always. A rough app with a great pitch beats a great app with no pitch.
Runner is never idle: seed data → facts for the deck → fixtures → screenshots → QA → demo-backup.mp4. Content and the clock are the job; the demo path is theirs to protect.

Phases

sequential for the driver
PHASE 01

Idea15 min

  • Ask the user first — no idea? get it from them. The gate blocks until answers are recorded
  • Restate as <who> uses it to <win>, because <differentiator>
  • Max three questions, and only if genuinely blocking
  • Pick one core feature — everything else goes to an "if time permits" list
  • Write the HACKATHON.md state file
PHASE 02

Spec15 min

  • SPEC.md: pitch, core feature, three-step demo path, stack, cut list
  • Default stack: single-file static HTML — zero install, fastest to a demo. Vite + React only if the idea needs multiple screens, routing, or an npm-only library
  • Non-goals in writing: auth, deployment polish, tests beyond a smoke test
  • git init and commit phase: spec
PHASE 03

Build120 min

  • Demo path first, in order — no abstractions "for later"
  • A step dragging? Cut scope, log the cut, keep moving
  • Verify the core feature runs, then commit phase: build
Clock check: past half the budget with no end in sight → jump to Phase 05. Deck over features.
PHASE 04

UI polish30 min

  • Real-looking seed data — never lorem ipsum on the demo path
  • Make the wow moment loud: one big number, one chart, one animation
  • Hardcode anything fragile; the demo path must never error
  • One accent color. No design exploration.
PHASE 05

Deck4–5 slides

  • Title · The problem · What we built · Projected impact · What's next
  • Slide 04 numbers are labeled demo/projection — never presented as traction
  • Generated by the harness: deck --init (Marp slides.md) or deck --init --html (bespoke slides.html with the animation engine)
PHASE 06

Script≤ 2 min

  • Beats: one slide + one sentence (≤ 12 words) + one action
  • Beat order mirrors the demo path; close on the wow line, verbatim
  • Ship a 30-second version and three Q&A answers
  • Read it back as a numbered list so the team can repeat it
PHASE 07 · ALL HANDS

Rehearsefinal 30 min

  • Every beat maps to a real screen or button — fix the mismatches
  • Cold-restart smoke test: kill the app, start it, walk the whole demo path
  • Record demo-backup.mp4 — live demos fail, video doesn't
  • Time the run-through out loud. Over two minutes? Cut the how-it-works beat first.
All three present. Every member must be able to say at least one beat — if the demo dies, anyone can carry it.

Recovery rules

when it goes sideways

Lost your place

  • Read HACKATHON.md first, continue from Next:
  • Never re-ask a question already answered in SPEC.md

Ambiguous decision

  • Take the fastest reasonable path, log it, keep moving
  • Hackathons don't wait for perfect information

“So how did you build this?”

  • Answer plainly: "We used AI coding tools to build fast." Transparency is the whole strategy.

THE FINDING

Harness > modelon hard tasks

  • The same model spans 0/5 to 4/5 across harnesses on the five long-horizon tasks — the tool around the model decides.
  • Easy tasks are saturated: every harness × model passes the eight routine React/Expo tasks, so they say nothing about tool choice.
  • Numbers are directional — n=1 per condition, timeouts folded into failure, cost under-reported on timed-out runs.
WHAT TO DO ABOUT IT

For this hackathon

  • pi and opencode top the weighted ranking — pick one and commit; don't shop tooling mid-build.
  • The demo path is long-horizon work: budget for timeouts, not just wrong answers.
  • Cost tracks tokens, not wall-clock — the slower harness can be the cheaper one.
Score the pair, not the model. A headline number describes a harness + model together, never model quality alone.
